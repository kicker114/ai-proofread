## 三、系统性差异分析

### 3.1 范式差异：重写 vs 标注

**pub + political** 的核心范式是**标注审校**（annotation-first）：
- 发现以批注形式呈现（`💬待核`），不自动改文
- 修订助手（pub 管线）可以对 `must_fix` 做字符级修订，但绝大多数政治发现被分类为 `verify`
- 结果：**人工审查者能在 Word 批注面板中逐一确认/拒绝，适合出版终审流程**

**ai-proofread max** 的核心范式是**发现即改写**（discover-and-rewrite）：
- JSON 发现模式下，LLM 直接输出修正后的句子
- `match_similar_text` 做模糊定位回写，不加批注
- 结果：**精修版全文可直接使用，但缺乏人机交互的批注层，适合初稿阶段快速迭代**

### 3.2 分层设计 vs 单次通读

pub+political 管线有**明确的层次分工**：

```
pub 管线（语言质量）
  ├── 修订助手 (must_fix 字符级修订)
  ├── 知识核查 (polish/verify 批注)
  └── 12 技能并行 (A/B/C/D/G 组)
       └── 政治管线叠加 (officecli --source 审阅版)
            ├── 政治审校批注 (verify only)
            └── 关键词确定性扫描
```

每一层独立运行、独立回写，后面的层**叠加**在前面的产物上（`officecli --source`）。最终 DOCX 中有**165 修订助手修订 + 2583 寇艺明修订 + 104 批注**的多层叠加。

ai-proofread max 是**单次通读**：所有检查（确定性 + LLM）× 所有阶段（0a/0b/0c/1/2/3）一次跑完，产出 1 份精修版 + 1 份综合报告。

**优劣**：
- 分层设计更适合**多人协同**（责编→编辑→政治审读→终审，各管各的 layer）
- 单次通读更适合**个人快审**（一个作者/编辑自己跑一遍，看完报告直接改）

### 3.3 政治合规深度

**政治管线独有能力**（max 管线不具备）：
- **159 个关键词分类扫描**（territory/organization/ideology/leader/event/sensitive_person）
- **5 维度评估框架**（历史事件/历史人物/敏感议题/意识形态/数据可靠性）
- **术语合规映射**：65 组 forbidden→approved 对（如 "中产阶级→中等收入群体"）
- **联网查证**（搭配 `--verify`）：新华社/人民日报/政府白皮书核实官方出处
- **官方表述知识**：政治管线能区分"习近平经济思想"和"习近平新时代中国特色社会主义经济思想"的发布时间差异，提示使用统一定名

**max 管线能做的**（政治管线也能做但被 verify 限制）：
- "习近平→习近平同志"——max 自动改了，政治管线只批注

### 3.4 确定性检查对比

| 检查类型 | ai-proofread max | pub + political |
|----------|-----------------|-----------------|
| 汉字规范（繁体/异体/表外） | ✅ TGSCC 8105 字查表 | ❌ 无 |
| 异形词/不规范词形 | ✅ 离线词典 3000+ 组 | ❌ 无（pub 管线有 2521 组《现汉》首选词扫描，但不同文件） |
| 章节层级 + 编号连续性 | ✅ structure_checker（11 条诊断） | ✅ global_checks.py 的 check_heading_numbering |
| 政治关键词确定性扫描 | ❌ 无 | ✅ 159 关键词 + 65 术语映射 |

**结构检查诊断的 11 条发现**（全部为 `目` 级编号问题，如 `目 需递增或重启为1：0→4094`）表明：max 管线的 structure_checker 规则（`rules.example.json`）的"目"模式（`\d+\.`）在这个文档里大量匹配了非标题文本（如年份 "2024."、数据 "4094."），产生了大量误报。**这是规则不适配的问题，不是引擎 bug**——需要为该文档定制规则 JSON。

## 四、根因分析

两套系统产出的差异，根因在于**设计哲学的根本分叉**：

### 4.1 「发现即修改」 vs 「发现即标注」

| | ai-proofread max | pub + political |
|--|-----------------|-----------------|
| **哲学** | LLM 可以做对的事，直接改 | LLM 可能出错，标注给人审 |
| **适合阶段** | 组稿/编加（作者快速迭代） | 终审看版（出版前最后把关） |
| **人工负荷** | 低（精修版可直接用） | 高（每条批注需逐一确认/拒绝） |
| **风险** | 误改不可逆（无批注回溯） | 无遗漏但慢 |

### 4.2 关注点不同

- **pub+political**：**出版合规导向**。关心的是"出版了会不会出事"——领导人表述、领土措辞、历史定性。这些发现都是 `verify`，因为一旦改错，责任在出版方。
- **ai-proofread max**：**语言质量导向**。关心的是"读起来顺不顺"——错别字、语法、标点、行文流畅度。这些发现可以自动改，因为改对改错都是语言层面的。

两者**互补而非替代**——一套好的出版审校流程应该同时有：
1. ai-proofread max 做**初稿阶段**的快审（语言质量、结构连贯性）
2. pub 管线做**编加阶段**的并行深度审校（12 技能全覆盖）
3. political 管线做**终审阶段**的合规把关（政治敏感关键词 + 术语 + 联网核实）

### 4.3 为什么 max 多发现 130+ 条而 pub 只多发现约 7 条

这不是"谁更强"的问题，是**分类粒度不同**：

- **max 的 JSON 发现模式**（`outputJSON` prompt）要求 LLM 输出**每个改动的句子对**，因此 149 条是一句一句的粒度
- **pub 的 issues[] 模式**要求 LLM 输出**每个逻辑独立的错误**，一条 issue 可能涵盖一个段落的多处同类问题

例：max 把"金融稳经济稳→金融稳则经济稳"、"二→二、"、"客户→投资者"各算 1 条（3 条）；pub 可能把它们合并为 1 条"表达润色"。

## 五、建议

### 5.1 对 ai-proofread max 的改进方向

1. **修复 structure_checker 误报**：为本书稿定制规则 JSON（"目"模式 `\d+\.` 在此文档应设为 `optional: true` 或修改 pattern 排除年份/数据数字）
2. **添加批注层**：精修版 `_refined.md` 可以同时输出每条修正的批注版本，让审查者看到"为什么改"
3. **引入质量门禁**：借鉴 pub 的 haiku anchor-rate monitor，当 LLM 置信度低时自动降级为批注

### 5.2 对 pub + political 管线的改进方向

1. **polish 升级为自动字符级修订**（已在 HANDOFF 中计划）：当前 political 管线全部 verify，可以给低风险类目（如 terminology_compliance 中的词形统一）升级为 polish + 字符级修订
2. **接入离线异形词库**：pub 管线已有 2521 组《现汉》首选词扫描；publish 管线可借鉴 max 管线的异形词离线词典（xh7 + yixingci）扩展

### 5.3 最佳实践组合

```
组稿阶段 → proofread max（快审，语言质量）
     │
     ▼
编加阶段 → proofread pub（12 技能并行，深度审校）
     │
     ▼
终审阶段 → proofread political（政治合规 + 联网核实）
     │
     ▼
签付印前 → proofread w（将所有发现回写 DOCX 审阅版，主编最终把关）
```
